## Goal
Ship `apps/web` to Vercel with no Go backend. The Next.js app reads `content/` directly.

## Why this works
The Go service does no real backend work — no DB, no auth (both stripped last commit), all reader state in localStorage. It's a read-through layer over `content/*.json` plus some precompute (sort books, simplify trad→simp, build a chengyu reverse-index). All of that is build-time work, not runtime.

## Architecture: build-time precompute + server-side reads

**New file: `apps/web/src/lib/content/`** — a TypeScript content layer that replaces `services/api/`. Two parts:

### 1. `scripts/build-content.ts` (runs at `prebuild`)
A Node script that runs once at build time and writes precomputed artifacts into `apps/web/.content-cache/` (gitignored):
- `books.json` — the sorted, projected books list (curriculum_order → tier S/A/B → slug), each catalog's `chapters[]` trimmed to the public shape, `available` defaulted to true. **This is the exact payload `/api/v1/books` returns today.**
- `char-index.json` — the 8.9MB index compacted to a lookup map keyed by both simplified and traditional forms, with `aliases` expanded. Plus the trad→simplified rune map derived from it. (~5-8MB; loaded once into the Next process, not per-request.)
- `chengyu-index.json` — the char→idiom reverse index (capped 8/rune), precomputed by scanning `chengyu-catalog/chapters/*.json` once.

Why precompute: the Go service builds the chengyu index and trad→simpl map at startup; on Vercel that work would happen on every cold start of every serverless function. Doing it once at build time is strictly better.

### 2. `apps/web/src/lib/content/index.ts` — drop-in replacement for `@/lib/api`
Same exported names and signatures: `getBooks`, `getChapter`, `getCharacter`, `getCharPinyinBatch`, `ApiError`, and all types (`Book`, `Chapter`, `ReadingUnit`, `WordSpan`, `CatalogChapter`, `CharacterDetails`, `CharPinyinEntry`). It reads from the precomputed cache + raw `content/` files using `fs.readFile`/`JSON.parse`, replicating the 10 transformations the Go service does today (numeric chapter ID normalization, on-response simplification of chapter title/summary/text, char batch dedup + 2000 cap + first-pinyin-only, the `available` default, etc.).

This means **zero changes to any call site** — every server component, client component, and route handler keeps importing from `@/lib/api`. We just swap that module's implementation from "fetch from Go" to "read from disk."

### 3. Route handlers for the two client-side calls
Create `apps/web/src/app/api/v1/characters/[char]/route.ts` and `apps/web/src/app/api/v1/characters/batch/route.ts` — thin handlers that call the same in-process functions and return the same JSON. These satisfy the two client components (`CharBreakdown.tsx` popover, `ReviewChars.tsx` saved-words panel) that fetch from `/api/v1` at runtime. The browser keeps hitting `/api/v1/...`; it just lands in a Next route handler instead of being rewritten to Go.

Remove the `rewrites()` block in `next.config.js` (no Go to proxy to). Update the `BASE` constant in `api.ts` so both server and client resolve to `/api/v1` via the route handlers — actually the client side already does; only the `typeof window === "undefined"` branch needs to change to also use `/api/v1` (route handlers are reachable same-origin from the server too, or we can call the functions directly since they're in-process).

### 4. `vercel.json` + package wiring
- Set `buildCommand` to run the prebuild script then `next build`.
- Configure `installCommand` (the repo uses pnpm in `apps/web` per `pnpm-lock.yaml`; Vercel needs `pnpm install`).
- Root directory: `apps/web`.
- Copy/symlink `content/` so it's reachable at build time — either Vercel's "root directory" stays at repo root and we point `buildCommand` into `apps/web`, or we set the content path via env and ship `content/` as part of the deploy. Cleanest: keep Vercel root = repo root, set `cwd: apps/web` for the build, and the content layer reads `../../content` (resolved at build, baked into the cache).

## Validation
- Run `pnpm build` locally with `API_BASE_URL` unset — every page must render with no Go process running.
- Run the existing Go server tests' expectations against the new TS layer's output for one book + one chapter + one char to confirm shape parity (the test file `services/api/internal/httpapi/server_test.go` documents the contract).
- Click a character popover locally, open the dashboard — both client paths must work via the new route handlers.
- Then `vercel --prod` (or link via the dashboard).

## What this does NOT do
- Does not delete `services/api/` — it stays for local/dev parity and as the source of truth for the response shapes. You can delete it later if you want.
- Does not change the on-disk `content/` format.
- Does not add caching headers, ISR, or static generation yet — that's a follow-up. First make it correct, then make it fast.
